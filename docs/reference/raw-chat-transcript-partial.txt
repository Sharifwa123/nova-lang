This is not a hypothetical edge case; it is the test case, and any resolution must make it behave the way every working developer expects.\n\nOPTIONS\nOption 1 — Implicit outer mutation (auto-detect: reassign if it exists outward, else create local)\n\nSET name = expr searches outward through enclosing scopes; if name already exists in some enclosing scope, mutate it there; otherwise create a new local binding.\n\nOption 2 — Distinct keyword for mutation (SET = declare-local-only; new keyword = mutate-existing)\n\nKeep SET's meaning exactly as already specified (§8.6: always local, always fresh). Introduce a second, explicit statement — e.g. CHANGE name = expr or UPDATE name = expr — whose only job is to walk outward through the scope chain, find an existing binding named name, and mutate it in place. Provide a dedicated accumulation construct instead (e.g., a built-in REDUCE/SUM-style operation, or requiring the loop to be expressed as a procedure that returns the accumulated value).\n\nTRADE-OFFS\n\nOption 1 (implicit auto-detect):\n\nFor: Zero new syntax. SET total = total + price \"just works,\" matching what a first-time reader probably expects, and matching what most working developers coming from Python/JavaScript are used to (Python's own total += x inside a loop, without nonlocal, actually does not work this way and is a well-known real Python beginner trap — which is itself evidence against this option, not for it, see below).\nAgainst — this is decisive: This reintroduces exactly the ambiguity §8.6 originally rejected: whether a given SET mutates an outer variable or creates a new local one now depends on a fact that isn't visible at the SET site — whether some enclosing scope happens to already have a variable of that name. This is non-local reasoning by construction. Worse, it interacts badly with shadowing (§8.5): if a block first shadows total locally and then later in the same block writes SET total = ... again, does that second SET update the local shadow or was the shadow never \"real\" because the outward search always wins? This creates a genuine grammatical ambiguity between two decisions (§8.5 shadowing, §8.6 mutation) that were designed independently and now conflict. It also is silently dangerous for typos: if a developer means to create a new local variable subtotal but mistypes total, and an outer total happens to exist for unrelated reasons, the typo silently mutates someone else's state instead of erroring — a real correctness hazard, and one that gets worse, not better, as programs grow (the \"some outer scope happens to have this name\" condition becomes more likely by accident in a large PAGE/API/DATA program with many named things in play, which is precisely the direction NOVA is headed). Rejected.\n\nOption 4 (no mutation, functional-only accumulation):\n\nFor: Maximum predictability — there is no mutation to reason about at all outside a procedure's own local scope. This is the \"purest\" answer and matches the general safety instinct behind §8.2/§8.6.\nAgainst — decisive for NOVA specifically: This fights the stated core philosophy directly. NOVA's examples are explicitly imperative (SET stock = stock - 1, SET total = total + price) and the whole design brief describes NOVA as reading like natural, ordinary instructions to a computer — \"natural enough for a human to understand immediately.\" Forcing every accumulation into a fold/reduce-style functional construct is a legitimate design for a functional language, but it is a different language than the one this project is building, and it would make the given test case inexpressible in the form given, contradicting the instruction to treat it as a required, working test case. Also, purely functional accumulation still needs some answer for procedures that want to build up a result across many steps (order processing, running totals, session state) — deferring this to \"always return a new value and thread it through\" pushes the same problem into every future feature (WHEN event handlers, API request processing) that will need to build up state across steps. Rejected — wrong fit for NOVA's stated identity, not wrong in the abstract.\n\nOption 3 (explicit SHARE-style declaration):\n\nFor: Closest to the safest possible design — explicit, auditable, matches how modern systems languages (Rust's borrow rules, even Pascal's var parameters) handle mutable aliasing, which matters a great deal once NOVA's long-term concurrency story exists (mutable state that crosses a scope boundary is exactly the thing concurrency bugs are made of, so making every case explicit and greppable is valuable insurance for a language planning to eventually have concurrent execution).\nAgainst: This is meaningfully more ceremony for the single most common looping pattern in the language — every accumulation loop now needs a declaration line before it does the obvious thing. For a language whose stated goal is that a beginner-readable example like FOR EACH price IN prices should read immediately, requiring SHARE total (or similar) above it adds a concept (a scope-crossing declaration) that has to be taught before the very first non-trivial loop works. It's not wrong engineering — it's front-loaded ceremony for a case common enough that most languages don't require it (C, Java, JavaScript, Python-with-nonlocal-avoided-by-just-using-var-scoping — none of them require declaring intent to mutate an outer local in the common case; only genuinely safety-critical or highly concurrent languages do, and NOVA isn't there yet).\n\nOption 2 (distinct keyword: SET stays pure-local; new keyword mutates outward explicitly):\n\nFor: Every property that made §8.6's original SET rule good is preserved without exception — SET continues to mean exactly one thing, unconditionally, everywhere, forever: \"declare or update a binding in the current scope only.\" The new keyword's entire job is the opposite: unconditionally search outward and mutate an existing binding, erroring if none is found (no ambiguity with declaration at all — it's a pure mutation operator, never a declaration operator). This means both operations are individually unambiguous and require zero non-local reasoning to understand: seeing the keyword alone tells you exactly what class of thing is happening, with no dependency on what happens to exist elsewhere. It also reads honestly: the developer is explicitly saying \"I intend to change something outside this block,\" which is a true, meaningful, and small piece of information — not ceremony, but signal. It composes cleanly with shadowing (§8.5 is completely untouched — shadowing is purely a SET/declaration concept; the new keyword doesn't declare anything, ever, so it can't interact with shadowing rules at all). It also composes cleanly with the future concurrency/events/security stories: a language where \"this specific line mutates shared state that crosses a scope boundary\" is lexically distinguishable from \"this line declares a local\" is a language whose static analyzer, race-detector, or security auditor can grep for exactly the lines that matter, later, for free.\nAgainst: One more keyword to learn, though it's a small, focused addition, and the test case is written with exactly one extra word rather than a SET-alone reading.\nRECOMMENDATION\n\nAdopt Option 2: introduce a new keyword, CHANGE, whose sole grammar and semantics are \"mutate an existing binding found by searching outward through the scope chain,\" while leaving SET's semantics from §8.6 completely untouched.\n\nCHANGE name = expr behaves as follows: search the scope chain outward starting from the current scope; if a binding named name is found, update its value in place (in whichever scope it actually lives), subject to the same type-compatibility rule as SET reassignment (§4.1 — no silent retyping); if no binding named name exists anywhere in the chain, this is a semantic error (\"total\" is not defined. CHANGE can only update a variable that already exists — use SET to create it.). CHANGE never creates a new binding, in any scope, under any condition. This makes CHANGE the exact structural opposite of SET: SET always writes to \"here\" (and creates if needed); CHANGE always writes to \"wherever this actually lives\" (and never creates).\n\nThe required test case:\n\n\nnova\nSET total = 0\n\nFOR EACH price IN prices\n    CHANGE total = total + price\nEND\n\nSHOW total\n\ntotal is created once in the outer scope by SET, and the loop body updates that same outer binding on each iteration via CHANGE, reading its current accumulated value (total) and the current loop element (price) on the right-hand side, then storing the new sum back into the outer binding. After the loop, SHOW total prints the correct sum, and the loop-body's own scope (per §8.4, a fresh scope per iteration for price) is never involved in holding the accumulator — it only holds the loop variable, exactly as already specified.\n\nWhy this beats Option 3 (explicit SHARE declaration) specifically: Option 3 solves the same safety problem but requires a declaration step before the mutation, whereas Option 2 makes the mutation itself self-describing — the keyword at the point of use tells the whole story, with nothing to declare in advance and nothing to keep in sync if the loop body grows to reference more outer variables later. It's strictly less ceremony for equivalent auditability, because CHANGE is already, by itself, the complete, greppable signal Option 3 was trying to achieve via a separate declaration.\n\nWhy this beats Option 1 despite requiring new syntax: Option 1's entire appeal was \"no new syntax,\" but that convenience was purchased by making SET's behavior context-dependent again — exactly the property §8.6 was written to eliminate. A two-keyword system where each keyword has one unconditional meaning is a stronger foundation than a one-keyword system whose meaning depends on ambient scope contents, even though it costs one more word in the vocabulary.\n\nLong-term dividend, stated directly: every future domain this language grows into (WHEN event handlers mutating shared UI/application state, API handlers mutating request-scoped or session state, eventual concurrent execution where two tasks might touch the same binding) benefits from having a single, lexically distinct, statically greppable statement kind that means \"this line crosses a scope boundary to mutate existing state.\" A security review, a race-condition analysis pass, or an AI-assisted refactor can all be built around finding every CHANGE in a codebase and knowing, without executing anything, exactly which lines can affect state outside their own block — a property SET-only or auto-detecting designs cannot offer.\n\nIMPACT\n\nThis decision touches: §2.6 (keyword table), §4.1 (assignment section — needs a sibling subsection), §6.1 (statement grammar list), §8.6 (rewritten in full), §11 (new diagnostic for CHANGE on an undefined name), §12 (AST), §13 (semantic analysis responsibilities), §15 (extension points — CHANGE's interaction with future procedure/event scopes should be noted), §17 (implementation contract).\n\nDECISION\n\nAdopted as stated. The ancestor binding is not deleted, altered, or otherwise affected — it simply stops being what resolve() returns while the nearer one is in scope, and resumes being reachable the instant the shadowing scope ends (because that scope, and its binding, is destroyed — §3).\n\n6. The Type Representation Must Change (this is the load-bearing decision)\n\nDECISION: NovaType (currently a flat string union: \"integer\" | \"decimal\" | \"text\" | \"boolean\" | \"list\" | \"none\") becomes a proper tagged type structure:\n\n\ntypescript\ntype NovaType =\n  | { tag: \"integer\" }\n  | { tag: \"decimal\" }\n  | { tag: \"text\" }\n  | { tag: \"boolean\" }\n  | { tag: \"none\" }\n  | { tag: \"unknown\" }              // renamed from the overloaded use of \"none\"\n  | { tag: \"list\"; element: NovaType }\n  | { tag: \"record\"; fields: Map<string, NovaType> };\n\nRATIONALE: This is the change everything else depends on, so it's worth being explicit about why a flat enum can't be patched instead. A flat \"list\" tag can't say list of what — that's exactly the gap that makes FOR EACH's loop variable UNKNOWN today. Once list needs an element type, NovaType can no longer be a flat enum; it has to be a recursive structure, the same way ASTs are recursive. Records need the same thing one level further: a record type must carry its field names and each field's type, recursively.\n\nDECISION — separating \"none\" from \"unknown\": v0.1 conflated two different meanings under \"none\": (a) the actual runtime value a procedure returns when it falls through without RETURN (a real, meaningful value — §3, §9.4), and (b) \"the analyzer doesn't know this type yet\" (parameters, loop variables — a static placeholder, not a value). These must be split now, because a record or list type needs to know unambiguously whether a field is genuinely typed \"none\" (a procedure result stored somewhere) versus \"not yet inferred\" — conflating them would make record field-type comparison unreliable. unknown is the new placeholder tag; none is reserved exclusively for the real \"no value\" runtime case.\n\nALTERNATIVE CONSIDERED: Keep NovaType flat and track element/field types in a side-table keyed by variable name. Rejected: this reintroduces exactly the \"information not visible at the point you need it\" problem the scope model was designed to avoid — a side-table has to be kept in sync with scope entry/exit by hand, which is a correctness hazard for no benefit over just making the type itself recursive.\n\n2. Lexical Changes\n\nDECISION: {, }, [, ] move from \"not in v0.1\" to real, tokenized punctuation. : (already tokenized but unused since v0.1 §2.8) gets its first real grammar use: separating a record field name from its value in a literal.\n\n\nname : text            <- NOT yet valid (that's DATA's future field-type syntax, still deferred)\n{ name: \"Widget\" }     <- valid NOW: a record literal's field-name : value separator\n\nDECISION (resolving a possible confusion directly): These are two different uses of : that must not be conflated. DATA's eventual name : text declares a field's type (a type annotation). A record literal's name: \"Widget\" provides a field's value (a key-value pair). This spec only implements the second. The token is identical; the position in the grammar disambiguates them, and since DATA has no grammar yet, there's no actual ambiguity to resolve today — only a note-to-self that DATA's design must not casually reuse : in a way that becomes ambiguous with record-literal syntax once both exist. Flagging this now, in writing, is exactly the kind of forward-compatibility check the project's discipline calls for.\n\n3. Grammar\n\nebnf\nprimary          ::= literal\n                    | identifier ( \".\" identifier )*\n                    | \"(\" expression \")\"\n                    | list-literal\n                    | record-literal\n\nlist-literal     ::= \"[\" ( expression ( \",\" expression )* )? \"]\"\n\nrecord-literal   ::= \"{\" ( field-init ( \",\" field-init )* )? \"}\"\nfield-init       ::= identifier \":\" expression\n\nnova\nSET numbers = [1, 2, 3, 4, 5]\nSET names = [\"Alice\", \"Bob\", \"Carol\"]\n\nSET product = { name: \"Widget\", price: 10, stock: 25 }\nSHOW product.name\n\nSET products = [\n    { name: \"Widget\", price: 10 },\n    { name: \"Gadget\", price: 25 }\n]\n\nFOR EACH product IN products\n    SHOW product.name\nEND\n\nDECISION: An empty list [] is legal syntax. Its element type cannot be determined from the literal alone — see §5 (type inference for empty collections) for how this is handled without guessing wrong.\n\nDECISION: An empty record {} is legal syntax and has the record type with zero fields — a real, if unusual, type, not an error. This is consistent with v0.1's existing \"empty block is permitted, not special-cased\" philosophy (§6.1).\n\nDECISION: Field names in a record literal must be unique within that literal. A duplicate field name is a semantic error (new diagnostic, see §7), not last-write-wins overwriting — silent overwrite would hide a likely typo, which the language's error-message philosophy exists specifically to catch.\n\n4. AST Additions\n\ntypescript\ninterface ListLiteral {\n  readonly kind: \"ListLiteral\";\n  readonly elements: Expression[];\n  readonly span: SourceSpan;\n}\n\ninterface RecordField {\n  readonly name: Identifier;\n  readonly value: Expression;\n}\n\ninterface RecordLiteral {\n  readonly kind: \"RecordLiteral\";\n  readonly fields: RecordField[];\n  readonly span: SourceSpan;\n}\n\nBoth join the Expression union in ast.ts, slotting into primary exactly like every other expression form — no special-casing needed elsewhere in the parser's precedence chain, since these are unambiguous, self-delimiting ([...]/{...}) productions.\n\n5. Type Inference and Structural Comparison\n\nDECISION — list literal typing: A non-empty list literal's type is list of the unified type of its elements. \"Unified\" here reuses the existing v0.1 widening rule (§3/§4.1: integer widens to decimal) generalized to a list: if all elements are integer, the list is list<integer>; if elements mix integer and decimal, the list is list<decimal> (each integer element widens); if elements are structurally-compatible records (§6), the list is list<record<...>> using the unified record shape; if elements are of genuinely incompatible types (e.g., mixing text and integer), this is a semantic error — DECISION: NOVA does not have heterogeneous lists in v0.2. Every element must unify to one element type. This is consistent with v0.1's core stance that types are meaningful and checked, not a dynamic grab-bag (§4.1's rationale against JavaScript-style silent flexibility applies identically here).\n\n\nnova\nSET mixed = [1, 2.5, 3]      # OK: unifies to list<decimal>\nSET bad = [1, \"two\", 3]      # ERROR: cannot unify integer and text in one list\n\nDECISION — empty list literal typing: [] alone has type list<unknown> (using the renamed placeholder from §1). This is not resolved further at the point of the literal; if it's immediately used somewhere that pins down the element type — e.g., SET x = [] \\n CHANGE x = ... is not yet meaningful since v0.1/v0.2 have no list-mutation operations — the type simply stays list<unknown> for now. DEFERRED, explicitly: list mutation operations (append, etc.) are not part of this milestone; []'s main use for now is as a FOR EACH iterable that legitimately iterates zero times, which requires no element-type resolution at all (the loop body never executes, so the loop variable's type is never actually needed).\n\nDECISION — record literal typing: A record literal's type is the record type whose fields map exactly to the literal's field names and each field value's inferred type, in the order given (order is not semantically meaningful for structural comparison, only for the AST/display).\n\nDECISION — structural record type comparison (the core new algorithm): Two record types are considered the same type if and only if they have exactly the same field names, and each corresponding field's type is the same (recursively, using this same comparison, and reusing the existing integer→decimal widening rule per-field). This must be a width-and-depth-exact comparison for v0.2 — DECISION, explicitly narrowing scope: NOVA v0.2 does not implement structural subtyping (a record with extra fields beyond what's required is not automatically compatible with a narrower expected shape). Two records are either the same shape or they're a type error; there is no \"close enough\" partial matching yet.\n\nRATIONALE for exact-match rather than subtyping: Structural subtyping (TypeScript's interface-style \"has at least these fields\" compatibility) is a well-understood and valuable feature, but it introduces real design questions — is subtyping allowed for FOR EACH unification across a list of records with different extra fields? Is it allowed for procedure parameters? These are legitimate future questions, not ones to answer as a side effect of shipping list literals. Exact structural matching is the smaller, more conservative choice that doesn't foreclose adding subtyping later (subtyping is a relaxation of exact matching, so it can be layered on without breaking programs that only ever relied on exact matching).\n\nDECISION — FieldAccess typing, finally real: expr.field type-checks by inferring expr's type; if it is a record type containing field, the access's type is that field's type. If expr's type is record but does not contain field, this is a semantic error (new diagnostic, §7) citing the record's actual known fields — directly serving the error-message mandate (\"here's what you have, here's what you asked for\"). If expr's type is anything other than record or unknown, field access is a semantic error stating that the value has no fields at all. If expr's type is unknown (a parameter or loop variable whose type isn't statically known — still possible when list elements are unknown), field access is permitted to pass statically (deferred to a runtime check), exactly mirroring how numeric/boolean operations already treat unknown permissively in v0.1's analyzer.\n\n6.
